# 项目总览与维护指南

> 本文从仓库当前结构出发，说明项目由哪些部分组成、各部分如何协作，以及日常改动应遵循的维护边界。产品需求见 `prd/PRD.md`；调率站的业务规则、技术实现和本地定制分别见 `doc/` 下的专题文档。

最后核对：2026年8月21日

## 一、项目定位

这是一个以 **Hugo + Blowfish** 构建的中文个人博客，同时在静态资源中托管了独立的《燕云十六声》调率站。两者共享同一个 Git 仓库和 GitHub Pages 发布链路，但运行形态不同：

```text
Hugo 博客内容与主题
  └─ 生成文章、首页、菜单、搜索索引

静态调率站（/tools/yysls-tiaolv/）
  ├─ 原生 HTML/CSS/JavaScript 交互层
  ├─ 浏览器本地装备档案与可选云备份
  ├─ Q7 原版计算引擎
  └─ Rust/WASM 面板与流派计算模块
```

调率站是仓库中功能与维护成本最高的子系统；博客是站点入口、内容承载和部署容器。

## 二、目录与职责

| 路径 | 职责 | 修改注意事项 |
| --- | --- | --- |

## 三、调率站的分层边界

调率站的计算链和用户功能必须分开看待：

```text
装备 / 方案 / 转律覆盖层
          ↓
app.min.js + local-customizations.js
          ↓
excel-runtime.js（统一输入与结果归一化）
          ├─ Panel WASM：配置 → 36 项最终面板
          └─ 当前流派 Excel WASM：面板 → DPS / 毕业率
          ↓
毕业率、培养、词条收益、转律建议、最佳配装
```

关键原则：主页和所有分析入口都要复用同一计算链；方案转律只用覆盖层模拟，不能改写装备库原词条。

生产前端中，`index.html` 的脚本加载顺序和版本查询参数是运行时契约。`local-customizations.js`、`cloud-backup.js`、最佳配装转律链路、装备等级与备份迁移都属于本站功能，不能因同步上游而丢失。

## 四、数据与状态

核心计算在浏览器本地执行。装备、角色、方案和转律状态主要保存在 `localStorage`，并按角色隔离；完整 JSON 备份是迁移与恢复的权威载体。Supabase 仅用于可选云备份，且采用本地优先、哈希去重和冲突暂停策略。

数值资产有两条独立来源：

| 引擎 | 权威来源 | 本地例外 |
| --- | --- | --- |
| Q7 原版 | `yysls.leoq7.com` 的完整引擎与工作簿体系 | 赛季抗性固定覆盖为 `2.45` |

详细同步边界以根目录 `AGENTS.md` 和 `doc/tiaolv-local-customizations.md` 为准。

## 五、构建、发布与当前风险

本地 Hugo 构建是所有文档、博客或调率站修改的基本门禁。涉及调率站的改动还必须运行：

```bash
./skills/tiaolv-site-checks/scripts/check_tiaolv_customizations.sh
hugo build
```

项目约定使用 `skills/auto-site-publish/scripts/publish_site.sh` 构建、暂存指定路径、提交并推送。实际发布前还应核对以下条件：

1. 仅暂存本次任务文件，避免把工作区中无关的未跟踪文件一并发布；
2. 生产远端 `origin` 已配置，且当前分支可推送；
3. GitHub Actions 监听的分支与实际推送分支一致。

截至本文核对时，当前本地分支为 `master`，未发现配置的 Git 远端；`.github/workflows/hugo.yaml` 仅监听 `main`。因此，即使本地构建成功，直接推送 `master` 也不会触发该工作流，且无 `origin` 时发布脚本无法完成推送。恢复自动发布前，应统一默认分支、工作流触发分支和远端配置。

## 六、维护决策表

| 变更类型 | 正确入口 | 最低验证 |
| --- | --- | --- |
| 博客内容、主题参数、普通静态资源 | Hugo 内容/配置直接修改 | `hugo build` |
| 调率站 UI/业务逻辑 | 本地前端；保留缓存版本与站点更新时间规则 | 定制检查 + Hugo 构建 |
| Q7 引擎或工作簿更新 | `skills/tiaolv-q7-engine-update/` | Q7 parity、隔离检查、构建 |
| 本地前端/定制改动 | 本地前端；保留缓存版本与站点更新时间规则 | `skills/tiaolv-site-checks/` + Hugo 构建 |
| 文档或 PRD 更新 | 保持产品/规则/实现/定制四类文档职责清晰 | Markdown 链接检查 + Hugo 构建 |

## 七、建议的后续治理

1. 先修复发布链：决定以 `main` 还是 `master` 为唯一发布分支，并配置 `origin`。
2. 为工作区建立清晰的初始提交或 `.gitignore` 策略，避免主体文件长期全部显示为未跟踪，降低误提交风险。
3. 把调率站的高风险验收命令收敛为 CI 可执行任务，特别是定制检查、JavaScript 语法检查和关键 parity 测试。
4. 继续将 `app.min.js` 中高耦合的本地功能逐步抽到有边界的模块，同时先补回归测试，避免同步和小改动引入交互回归。
